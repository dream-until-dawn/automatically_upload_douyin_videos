# 测试策略

> 指导原则：**永远绿的测试等于没有测试。**
> 每一条成功路径，都必须有对应的失败路径测试与之配对；
> 每一个错误码，都必须有一条测试能真实地把它逼出来。

## 1. 测试分层

| 层级 | 目录 | 跑什么 | 是否启动浏览器 |
| --- | --- | --- | :---: |
| 单元测试 | `tests/unit/` | 纯逻辑：配置解析、错误码映射、轻提示语义翻译、时间计算 | 否 |
| 集成测试 | `tests/integration/` | 真实 Playwright 驱动本地模拟页面，跑完整步骤与编排 | 是 |
| 冒烟脚本 | `scripts/` | 连真实抖音账号的人工验证，**不进自动化测试** | 是 |

## 2. 本地模拟页面

集成测试不依赖抖音线上站点——线上页面不可控、需要真实账号、会产生真实发布行为。

取而代之，`tests/fixtures/pages/` 下维护一套 **静态 HTML 模拟页**，
复刻创作者中心发布页的关键 DOM 结构与交互行为：

- 与真实页面一致的选择器特征（`input[type=file][name=upload-btn]`、
  `contenteditable` 编辑器、下拉框、单选标签、弹窗容器等）。
- 与真实页面一致的轻提示行为：通过动态插入 DOM 节点弹出提示文本。
- **可编程的失败注入**：通过 URL 查询参数控制模拟页的行为，
  例如 `?scenario=upload_failure&delay=500` 表示 500ms 后弹出「上传失败」。

这样就能在毫秒级、零副作用的前提下，稳定复现每一种异常。

### 2.1 模拟页的可信度边界

模拟页验证的是 **「选择器写法 + 交互时序 + 错误分支」**，
它不能保证真实页面不改版。因此：

- 真实页面的结构验证靠人工冒烟脚本，按需执行。
- 选择器全部集中在 `browser/selectors.py`，模拟页与真实页共用同一套常量，
  避免出现「测试用一套选择器、生产用另一套」的自欺。

## 3. 必测的反向场景

以下每一条都是独立的测试用例，断言 **具体的错误码**，不允许只断言「抛了异常」：

### 3.1 配置层

| 场景 | 期望码 |
| --- | ---: |
| 缺少命令行参数 | 18 |
| 配置既不是合法 Base64 也不是合法 JSON | 19 |
| JSON 合法但缺必填字段 | 19 |
| 必填字段为空字符串 | 3 |
| `publishTime` 非数字 / 超出 `1..300` | 归一化，不报错 |
| 浏览器路径不存在 | 4 |
| 用户数据目录不存在 / 是文件 / 为空目录 | 5 |
| 视频文件不存在 | 6 |

### 3.2 流程层（模拟页驱动）

| 场景 | 期望码 |
| --- | ---: |
| 页面无上传组件（视作未登录） | 9 |
| 模拟页弹出「上传失败」 | 10 |
| 上传始终无结论直至超时 | 11 |
| 模拟页弹出「服务异常」 | 13 |
| 挂车一般性失败（立即中止，不等待上传） | 14 |
| 自主声明下拉缺失 | 15 |
| 封面弹窗不出现 | 16 |
| 发布后弹出「发布失败」 | 17 |
| 发布设置单选项缺失 | 20 |
| 模拟页弹出「无法添加购物车」 | 21 |
| 模拟页弹出「暂不支持推广」 | 22 |
| 模拟页弹出「未搜索到商品」 | 23 |
| 标题编辑器缺失 | 24 |
| 全流程无任何结论直至总超时 | 12 |

### 3.3 竞速中止（本项目的核心承诺）

这组测试直接验证架构价值，**必须有**：

| 测试 | 断言 |
| --- | --- |
| 上传阶段早期弹出致命提示 | 进程在 **2 秒内** 返回对应错误码，而非耗满超时窗口 |
| 主流程卡在一个长等待中，此时哨兵命中 | 主流程被取消，长等待未走完 |
| 主流程正常成功 | 哨兵被取消，无悬挂任务，无 `Task was destroyed` 警告 |
| 取消发生时 | 浏览器上下文仍被正确关闭（断言清理钩子被调用） |
| 挂车失败且上传长时间无结论 | 立即返回挂车错误码，**不等待上传**（见 [ADR-0002](./adr/0002-fail-fast-on-cart-failure.md)） |

**耗时断言是这组测试的关键**：如果把「失败即中止」写坏成「失败后仍等满超时」，
功能测试依然会通过（错误码是对的），只有耗时断言能把这个退化抓出来。

### 3.4 契约一致性

| 测试 | 断言 |
| --- | --- |
| 错误码枚举 ↔ `docs/error-codes.md` 总表 | 码、名称、分类、可重试标记逐项一致 |
| 退出码范围 | 全部落在 `3..254` |
| 码值唯一 | 无重复占用 |
| JSON 结果结构 | 字段齐全、`code` 与进程退出码一致 |

文档与实现漂移会导致上游按错误的表做重试决策，因此把它变成一条会红的测试。

## 4. 防「假绿」机制

1. **耗时上界断言**：竞速中止类测试断言总耗时上界，退化即变红。
2. **禁止空断言**：异常测试必须断言错误码，不接受裸 `pytest.raises(Exception)`。
3. **超时全局封顶**：单条测试超时即失败，杜绝卡死伪装成运行中。
4. **同步阻塞哨卫**：一条专门的测试验证异步路径中不存在 `time.sleep`
   （在异步路径里调用它会钉死事件循环，使竞速中止彻底失效）。
5. **覆盖率只作参考**：不设覆盖率门槛，避免为凑数写无断言的测试。

## 5. 执行方式

```bash
uv run pytest                      # 全部
uv run pytest tests/unit -q        # 仅单元测试（秒级）
uv run pytest -m integration       # 仅集成测试（需浏览器）
```

集成测试使用 Playwright 自带的 Chromium，与生产环境指向本机 Chrome 的行为一致
（同为 Chromium 内核，DOM 交互语义无差异）。

### 并行执行

全量测试中约三分之一要启动真实浏览器，串行跑需要 10 分钟。
用 `pytest-xdist` 可以显著缩短：

```bash
uv run pytest -n 8          # 推荐：按机器核数调整
uv run pytest -n auto       # 按 CPU 核数自动决定
```

本机（16 核）实测：

| 方式 | 耗时 | 结果 |
| --- | ---: | --- |
| 串行 | 600s | 597 passed |
| `-n 8` 第一次 | 209.6s | 597 passed |
| `-n 8` 第二次 | 209.0s | 597 passed |

两次并行耗时几乎完全一致，说明并行是稳定的，不是碰巧跑通一次。

**并行度不写进默认配置**，原因是它与机器规格强相关：
并行会抬高负载，而本项目的耗时上界断言正是靠「失败即中止应当是秒级」来判定退化的。
并行度过高会让这些断言变得飘忽，那等于用核心保障换速度——不划算。

判断并行度是否合适，看这两条的实测耗时：

- `test_致命提示被哨兵捕获并立即中止`（阈值 15s）
- `test_挂车失败时不空等上传`（阈值 15s）

并行下它们仍应是秒级。一旦逼近阈值，就该调低并行度。

例外是 `tests/integration/test_launcher.py`：它必须显式传入可执行文件路径，
而自带 Chromium 的路径不能这样用（见 [探针结论](./probe-results.md) 的工程约束 3），
因此改用本机 Chrome，缺失时跳过而非失败。

## 6. 真实环境冒烟

```bash
uv run python scripts/smoke_real.py config.json            # 探测模式
uv run python scripts/smoke_real.py config.json --dry-run  # 演练模式
```

| 模式 | 行为 | 副作用 |
| --- | --- | --- |
| 探测（默认） | 打开发布页，逐个检查选择器能否命中 | 无 |
| 演练 | 执行上传、标题、挂车、封面等全部步骤 | 账号下留下一条草稿 |

两种模式都不会点击发布。发布步骤是 **从执行序列里排除掉的**，
而非「跑到那里再判断」——后者留有意外发布的可能，而真实发布不可撤销。

该性质由 `tests/unit/test_dry_run_steps.py` 强制校验，并做过变异验证：
把 `DRY_RUN_STEPS` 改回完整序列后，5 条测试变红，
日志中出现「哨兵命中 publish_failure」——证明发布按钮确实被点了。

冒烟脚本不进自动化测试：它需要真实账号，且结果依赖线上页面的当前状态。

### 探测必须精确复刻生产的查找方式

这一条是踩出来的。初版探测脚本对同一批选择器用了「差不多」的查找方式，
结果连续给出三类假结论：

| 探测脚本当时的做法 | 生产实际的做法 | 造成的假结论 |
| --- | --- | --- |
| `has_text="发布"`（子串匹配） | `exact=True`，编译成 `^发布$` | 命中「作品发布」，误报会点错按钮 |
| 全页查找挂车下拉框 | 在挂车区域容器 **内部** 查找 | 捞到「合集」的下拉框 |
| 对文件输入框做可用性判定 | `wait_for(state="attached")` | 对一个本就隐藏的输入框误报「不可用」 |

三者的共同点是：探测**看起来**在验证生产行为，实际验证的是另一套逻辑。
这比没有探测更危险——它会给出「全部命中」的虚假安全感，
也会把本来正常的元素报成改版，几次之后就没人再认真看结论了。

因此 `ProbeTarget` 显式携带 `exact`、`within`、`attached_only` 三个字段，
逐项对齐 `pipeline/steps/` 下真实的调用方式，
文本匹配也直接复用生产的 `build_text_matcher`。

另有两点同样影响结论可信度：

- **探测时机**：创作者中心各区块异步渲染，上传组件出现不代表页面就绪。
  实测同一页面两次探测拿到过不同的元素数量，因此探测前需静置数秒。
- **模式盲区**：发布设置区域要等视频开始上传后才渲染，探测模式必然看不到。
  这类元素用 `requires_upload` 标出并跳过，而不是算作失败——
  否则每次探测都报「页面已改版」，真正的改版反而被淹没。
