# 分期计划

> 每一期都以「可验证的产出」收口，不做没有验证手段的推进。
> 里程碑之间通过 git 分支隔离，合并主分支需经确认并打 tag。

## M0 · 地基与可行性验证 ✦ 当前阶段

**目标**：在写业务代码之前，把所有「可能推翻方案」的不确定性验证掉。

| 项 | 内容 | 验证标准 |
| --- | --- | --- |
| 文档先行 | 架构 / CLI 协议 / 错误码 / 测试策略 / 分期 | 本目录下文档齐备 |
| 工具链 | uv 管理依赖与虚拟环境 | `uv sync` 可重复构建 |
| 探针 A | Playwright 异步 API + 取消语义 | 能在长等待中途取消任务并立即退出 |
| 探针 B | **打包产物是否被 Windows 安全中心拦截** | 产物落盘后不被隔离，可正常执行 |
| 探针 C | 持久化上下文接管本机 Chrome | 能以指定用户数据目录启动并保持登录态 |

> **探针 B 是本阶段最高优先级。** 打包方案若不可行，会推翻交付形态，
> 必须在投入业务开发前得到结论，而不是等到最后一步才发现。

**交付分支**：`feat/foundation`

## M1 · 基础层

| 模块 | 内容 |
| --- | --- |
| `core/errors.py` | 错误码枚举、分类、可重试标记、异常体系 |
| `core/logging.py` | stderr 人读日志 / stdout 机读结果 双通道 |
| `core/events.py` | 事件类型定义与异步事件总线 |
| `core/waiting.py` | 可取消的异步等待、轮询、条件等待原语 |
| `config/` | 配置模型、Base64/JSON 解析、前置校验 |
| `system/processes.py` | 按用户数据目录精确清理进程 |

**验收**：单元测试覆盖全部配置层反向场景（见测试策略 3.1）与契约一致性测试（3.4），
此时尚无浏览器依赖，测试应在秒级跑完。

## M2 · 能力层与模拟页

| 模块 | 内容 |
| --- | --- |
| `browser/launcher.py` | 持久化上下文启动与安全关闭 |
| `browser/selectors.py` | 选择器集中登记 |
| `browser/actions.py` | 元素等待、可用性判定、滚动点击等原语 |
| `browser/toast.py` | DOM 观察器注入、轻提示语义翻译 |
| `tests/fixtures/pages/` | 可编程失败注入的模拟发布页 |

**验收**：集成测试能驱动模拟页，稳定捕获各类轻提示并翻译为正确的事件类型。

---

## M3 · 业务步骤

按依赖顺序实现 `pipeline/steps/`：上传 → 标题 → 发布设置 → 自主声明 → 挂车 → 封面 → 发布。

**验收**：每个步骤都有正向用例与至少一条反向用例，断言具体错误码（见测试策略 3.2）。

---

## M4 · 竞速编排

| 模块 | 内容 |
| --- | --- |
| `pipeline/context.py` | 流程上下文、待决错误机制 |
| `pipeline/runner.py` | 哨兵与主流程竞速、取消传播、总超时兜底 |
| `cli/` | 子命令分发、退出码与 JSON 结果输出 |

**验收**：竞速中止测试全部通过，**含耗时上界断言**（见测试策略 3.3）。
这是整个项目的核心承诺，此处不通过则不进入下一期。

## M5 · 打包与交付

| 项 | 内容 |
| --- | --- |
| 构建脚本 | 一键产出单文件可执行体 |
| 安全中心复验 | 在 M0 探针结论基础上，对完整产物复测 |

| README | 面向使用者的安装、配置、排障说明 |

**验收**：产物在干净环境下可直接运行完整发布流程。

---

## 里程碑纪律

1. 每期一条功能分支，期末合并前需经确认。
2. 合并主分支时打 tag（`v0.1.0` 起）。
3. 任何对架构红线的调整（分层、错误码语义、竞速机制）视为重大调整，须先确认再动手。
