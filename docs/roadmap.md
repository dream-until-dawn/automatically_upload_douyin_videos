# 分期计划

> 每一期都以「可验证的产出」收口，不做没有验证手段的推进。
> 里程碑之间通过 git 分支隔离，合并主分支需经确认并打 tag。

## M0 · 地基与可行性验证 ✔ 已完成

**目标**：在写业务代码之前，把所有「可能推翻方案」的不确定性验证掉。

| 项 | 内容 | 验证标准 |
| --- | --- | --- |
| 文档先行 | 架构 / CLI 协议 / 错误码 / 测试策略 / 分期 | 本目录下文档齐备 |
| 工具链 | uv 管理依赖与虚拟环境 | `uv sync` 可重复构建 |
| 探针 A | Playwright 异步 API + 取消语义 | 能在长等待中途取消任务并立即退出 |
| 探针 B | **打包产物是否被 Windows 安全中心拦截** | 产物落盘后不被隔离，可正常执行 |
| 探针 C | 持久化上下文接管本机 Chrome | 能以指定用户数据目录启动并保持登录态 |

三项探针均已通过，结论见 [探针结论](./probe-results.md)。

> **探针 B 是本阶段最高优先级。** 打包方案若不可行，会推翻交付形态，
> 必须在投入业务开发前得到结论，而不是等到最后一步才发现。

**交付分支**：`feat/foundation`

自检之所以要 **真的启动驱动**：打包产物最典型的故障是「能构建、不能跑」——
依赖被漏收、驱动在冻结环境下路径解析失败，这些在构建日志里完全看不出来，
import 成功也不代表驱动进程拉得起来。构建脚本把自检作为必经步骤。

**验收**：产物在干净环境下可直接运行完整发布流程。

已通过：52 MB 单文件产物，Defender 实时保护开启下按需扫描 `found no threats`、
未被隔离；自检 904ms 真实拉起 Playwright 驱动；四组命令行契约用例退出码与
JSON 完全一致。详见 [探针结论](./probe-results.md)。

## M6 · 运行时参数外置 ✔ 已完成

把「调用方有判断依据去调」的参数交出去，其余保持为内部实现细节。

| 项 | 内容 |
| --- | --- |
| `timeouts` | 8 个环节的等待上限，只写想改的项，其余保持默认 |
| `browserArgs` | 追加 Chrome 启动参数，黑名单拒绝会破坏运行前提的项 |
| `logLevel` | quiet / normal / debug |
| `skip` | 跳过非必要步骤，白名单挡住必要环节 |

全部可选，缺省时行为与此前完全一致。决策过程见
[ADR-0003](./adr/0003-runtime-options.md)。

**验收**：已通过。跳过步骤用成对测试验证——同一失败场景下，
不跳过则失败、跳过则成功，两者成对出现才说明跳过真的生效；
浏览器参数用自定义 User-Agent 真实启动浏览器再读回来验证，
而不是只断言「参数拼进了列表」。

## M7 · 可观测性与灵活性 ✔ 已完成

| 项 | 内容 |
| --- | --- |
| 纯内容视频 | `cartUrl` 改为选填，留空即自动跳过挂车 |
| 失败截图 | 失败时自动截取现场，路径回传给调用方。**默认开启** |
| 进度回报 | 按行输出步骤进度与心跳。**默认关闭** |

两处默认值相反，不是随意选的：截图只给结果 JSON 增加一个字段，
而进度会让 stdout 从一行变成多行。增字段是安全的，改变行数不是。
决策见 [ADR-0004](./adr/0004-progress-reporting.md)。

**过程中查出一个存在已久的缺陷**：写截图测试时，一条「同一上下文跑两次流程」的
用例失败，顺藤摸瓜发现 toast 监听器在页面导航后**从未**真正恢复过——
`add_init_script` 在 `document.body` 就绪前执行，`observe(null)` 抛错，
而「已安装」标记设在 observe 之前，导致随后那次 `evaluate` 被幂等保护挡掉，
观察器一个都没装上，却没有任何报错。

它一直没被发现，是因为生产流程打开发布页后不再导航，只走 `evaluate` 那条路径。
也就是说：文档声称的能力从未生效，而没有任何测试或日志能暴露这一点。

**验收**：已通过。进度与心跳用端到端测试验证，含「流程结束后心跳必须停止」
（变异验证：去掉取消后流程结束仍冒出 5 次心跳）。

## 里程碑纪律

1. 每期一条功能分支，期末合并前需经确认。
2. 合并主分支时打 tag（`v0.1.0` 起）。
3. 任何对架构红线的调整（分层、错误码语义、竞速机制）视为重大调整，须先确认再动手。
