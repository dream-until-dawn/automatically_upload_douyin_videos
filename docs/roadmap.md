# 分期计划

> 每一期都以「可验证的产出」收口，不做没有验证手段的推进。
> 里程碑之间通过 git 分支隔离，合并主分支需经确认并打 tag。

## M0 · 地基与可行性验证 ✔ 已完成

**目标**：在写业务代码之前，把所有「可能推翻方案」的不确定性验证掉。

| 项 | 内容 | 验证标准 |
| --- | --- | --- |
| 文档先行 | 架构 / CLI 协议 / 错误码 / 测试策略 / 分期 | 本目录下文档齐备 |
| 工具链 | uv 管理依赖与虚拟环境 | `uv sync` 可重复构建 |
| 探针 A | Playwright 异步 API + 取消语义 | 能在长等待中途取消任务并立即退出 |
| 探针 B | **打包产物是否被 Windows 安全中心拦截** | 产物落盘后不被隔离，可正常执行 |
| 探针 C | 持久化上下文接管本机 Chrome | 能以指定用户数据目录启动并保持登录态 |

三项探针均已通过，结论见 [探针结论](./probe-results.md)。

> **探针 B 是本阶段最高优先级。** 打包方案若不可行，会推翻交付形态，
> 必须在投入业务开发前得到结论，而不是等到最后一步才发现。

**交付分支**：`feat/foundation`

## M4 · 竞速编排 ✔ 已完成

| 模块 | 内容 |
| --- | --- |
| `pipeline/context.py` | 流程上下文（配置、页面、事件总线、时长预算） |
| `pipeline/runner.py` | 哨兵与主流程竞速、取消传播、总超时兜底 |
| `cli/` | 子命令分发、退出码与 JSON 结果输出 |

**验收**：竞速中止测试全部通过，**含耗时上界断言**（见测试策略 3.3）。
这是整个项目的核心承诺，此处不通过则不进入下一期。

已通过，并做了变异验证：把哨兵改成「命中致命事件也不中止」后，
三条竞速测试全部变红，错误码从 `PRODUCT_NOT_SUPPORTED(22)` 退化为
`UPLOAD_TIMEOUT(11)`，单条耗时从 0.45s 涨到 37s。
这说明耗时断言确实能抓出「错误码看着对、实则空等到超时」的退化。

## M5 · 打包与交付 ✦ 当前阶段

| 项 | 内容 | 状态 |
| --- | --- | --- |
| 构建脚本 | `scripts/build.ps1` 一键产出单文件可执行体 | 已完成 |
| 启动自检 | `selfcheck` 子命令，真正拉起 Playwright 驱动而非只做 import | 已完成 |
| README | 面向使用者的安装、配置、排障说明 | 已完成 |
| 安全中心复验 | 在 M0 探针结论基础上，对完整产物复测 | 待执行 |

自检之所以要 **真的启动驱动**：打包产物最典型的故障是「能构建、不能跑」——
依赖被漏收、驱动在冻结环境下路径解析失败，这些在构建日志里完全看不出来，
import 成功也不代表驱动进程拉得起来。构建脚本把自检作为必经步骤。

**验收**：产物在干净环境下可直接运行完整发布流程。

## 里程碑纪律

1. 每期一条功能分支，期末合并前需经确认。
2. 合并主分支时打 tag（`v0.1.0` 起）。
3. 任何对架构红线的调整（分层、错误码语义、竞速机制）视为重大调整，须先确认再动手。
