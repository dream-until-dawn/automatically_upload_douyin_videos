## 探针 A · 异步取消语义 —— 通过

**命题**：主流程阻塞在 Playwright 的长等待上时，哨兵能立即取消它并让进程退出，
而不必等那个长等待自己超时。这是 [ADR-0001](./adr/0001-async-race-abort.md) 的前提。

**方法**：主流程 `wait_for` 一个永不出现的元素（超时 30 秒），
哨兵在第 1 秒命中「致命事件」，两者竞速。

**结果**：

```
[竞速] 胜出任务: sentinel -> 致命事件：上传失败
[取消] 任务 pipeline 已被成功取消
[结果] 总耗时 1.47s（阈值 5.0s，若取消失效则应接近 30s）
```

**结论**：`Task.cancel()` 能穿透 Playwright 的异步等待，取消在一个调度周期内生效。
全异步竞速中止方案可行。

**复现**：`uv run python scripts/probe_cancel.py`

## 探针 B · 打包产物是否被安全中心拦截 —— 通过

**命题**：单文件可执行产物能通过 Windows 安全中心，不被隔离。
这是 M0 优先级最高的验证项——若不可行，交付形态必须整体重新设计。

**方法**：打包一个「最小但具代表性」的程序，它包含最容易触发启发式判定的行为：
单文件自解压、枚举系统进程（psutil）、携带 Playwright 驱动。
随后执行四步验证：产物是否幸存 → Defender 按需扫描 → 能否执行 → 执行后是否仍幸存。

**结果**：

| 检查项 | 结果 |
| --- | --- |
| Defender 实时保护 | 开启（引擎 1.1.26080.3，特征库 1.459.295.0） |
| 打包 | 成功，51.9 MB，20.5 秒 |
| 按需扫描 | `found no threats`，退出码 0 |
| 产物执行 | 退出码 0，输出符合预期 |
| 执行后仍存在 | 是（未被隔离） |

**结论**：PyInstaller 单文件方案在本机可用，工具链选型确定。

**保留意见**：本结论只覆盖本机当前的特征库版本。
未签名的可执行体在其他机器上仍可能触发 SmartScreen 的「未知发布者」提示
（那是信誉机制，不是病毒判定）。若分发范围扩大，代码签名是后续可选项。

**复现**：`powershell -ExecutionPolicy Bypass -File scripts/run_packaging_probe.ps1`

## 探针 C · 持久化上下文接管本机 Chrome —— 通过

**命题**：

1. 能以 `executable_path` 启动本机安装的 Chrome（复用登录态的前提）；
2. 能以指定 `user_data_dir` 启动持久化上下文；
3. 启动的进程命令行中带有 `--user-data-dir` 参数
   —— 这是「按用户数据目录精确清理残留进程」得以成立的前提。

第 3 点尤其关键：清理逻辑依赖命令行参数匹配，若 Playwright 不透传该参数，
清理会漏杀，浏览器随后会因目录被占用而启动失败。

**结果**（本机 Chrome 153.0.8010.48）：

```
[启动] 成功，页面标题: probe-c
[匹配] 按 --user-data-dir 命中的 Chrome 进程: [824, 14124, 24960, 25740,
                                              25808, 26128, 26792, 26836]
[落盘] 用户数据目录条目数: 16
[结论] 探针 C 通过
```

**结论**：三项命题全部成立。值得注意的是匹配到 **8 个** 进程——Chrome 会派生
多个渲染与工具子进程，它们共享同一个 `--user-data-dir`。这印证了清理逻辑必须
按目录匹配并批量终止，只杀主进程会留下子进程继续占用目录。

**复现**：`uv run python scripts/probe_chrome.py [chrome路径] [用户数据目录]`

| 检查项 | 结果 |

| 打包 | 成功，52 MB，20.5 秒 |

## 真实环境验证（v0.1.0 之后）

本节记录在 **真实抖音账号** 上的端到端验证。前面所有测试跑的都是本地模拟页，
模拟页能保证「生产代码与我们对页面结构的假设一致」，
但保证不了「这个假设与线上一致」——只有这一节能回答后一个问题。

**执行日期**：2026-09-20 ｜ **浏览器**：本机 Chrome 153.0.8010.48

### 选择器探测（零副作用）

八项关键选择器全部命中。其中两项需要特别说明：

| 元素 | 实测情况 |
| --- | --- |
| 发布按钮 | 页面上同时存在「作品发布」与「发布」两个按钮。精确匹配只命中后者，正确。 |

### 真实发布（经用户授权，可见性均为「仅自己可见」）

用生产入口 `python -m douyin_publisher publish <base64>` 执行，即上游实际的调用方式：

| 模式 | 退出码 | JSON code | stdout 行数 | 耗时 |

| 立即发布 | 0 | 0 | 1 | 75.7s |

**关键：返回 0 不等于设置生效。** 日期选择器是最容易「显示了值却没被采纳」的控件，
因此又去创作者后台的作品管理页做了只读核对：

| 作品 | 后台显示的发布时间 | 可见性 |

定时时间正是 24 小时后，两条均为私密。至此可以确认：
定时时间、可见性、标题与话题标签都真实生效，而非仅仅被填进了输入框。

完整流程在真实环境端到端可用，命令行契约（退出码 ↔ JSON）在真实发布路径上同样成立。

## 过程中确认的工程约束

探针执行过程中暴露了三条必须写入实现的约束，它们都不是设计推演出来的，
而是被真实报错逼出来的：

### 1. 标准流必须显式切到 UTF-8

Windows 控制台默认 GBK 代码页。直接输出中文会乱码，输出 emoji 会抛
`UnicodeEncodeError` 并导致进程异常退出——**日志本身成了故障源**。

落实：`core/logging.py` 的 `force_utf8_streams()` 在任何输出之前调用；
日志文案一律不使用 emoji。已验证该处理在 PyInstaller 冻结环境下同样有效。

### 2. PowerShell 脚本必须带 UTF-8 BOM

Windows PowerShell 5.1 读取无 BOM 的 UTF-8 脚本时，会按系统 ANSI 代码页解码，
中文注释变成乱码并直接引发语法错误。

落实：`scripts/*.ps1` 一律以 UTF-8 **带 BOM** 保存。

### 3. Playwright 自带 Chromium 的路径不能被显式传回

把 `playwright.chromium.executable_path` 取到的路径再显式传给
`launch_persistent_context(executable_path=...)`，会报 `spawn UNKNOWN` 而启动失败；
**不传** 该参数则一切正常。

三轮对照实验排除了两个初始猜测：

| 猜测 | 实验 | 结果 |
| --- | --- | --- |
| 用户数据目录含中文导致 | ASCII 与中文路径各跑一遍 | 两者都成功，**不是** 原因 |
| 与 headless 模式冲突 | headless 开关各跑一遍 | 两者都失败，**不是** 原因 |
| 自带 Chromium 路径不能显式传 | 自带路径 vs 本机 Chrome 路径 | 自带失败、本机成功，**是** 原因 |

**对生产无影响**：本程序本来就只会传本机 Chrome 的路径（那正是复用登录态的
前提），实测成功。受影响的只有测试——需要显式传路径的那几条改用本机 Chrome，
缺失时跳过（见 `tests/integration/test_launcher.py`）。

值得记录的原因是：第一个猜测若不验证就写进文档，会变成一条「用户数据目录不能
含中文」的假限制，而中文用户名在目标用户群里非常普遍。

### 4. PowerShell 中不可用 `2>&1` 捕获原生命令输出

PyInstaller 等工具把普通信息写入 stderr。在 PowerShell 5.1 中用 `2>&1` 捕获，
每一行都会被包装成 `NativeCommandError`，即使命令退出码为 0 也会被判定为失败。

落实：改用 `*>` 重定向到日志文件后再读取（见 `run_packaging_probe.ps1`
中的 `Invoke-Native` 辅助函数）。
