# ADR-0002 挂车失败立即中止流程

- **状态**：已采纳
- **日期**：2026-09-20

## 背景

发布流程中，「挂载购物车」位于视频上传与最终发布之间。
它有三种失败形态：

1. 达到挂车上限（错误码 21）
2. 未搜索到商品，多为已下架（错误码 23）
3. 其他一般性失败，如弹窗结构与预期不符（错误码 14）

一种可行的处置方式是「延迟判定」：挂车失败后不立刻中止，而是把错误记下来，
继续走完上传，等后续等待点拿到更多信息后再决定最终返回哪个错误码。
理由是挂车失败的具体原因有时要结合上传结果才能定性。

## 问题

延迟判定的代价很具体：

- 挂车已经失败的情况下，仍要继续等待视频上传完成——而上传可能耗时数分钟。
- 这段等待不产生任何价值：无论上传成功与否，任务都不会发布成功。
- 它与本项目的核心理念直接冲突。[ADR-0001](./0001-async-race-abort.md) 的
  全部努力就是为了让「已确定的失败」立即返回，而延迟判定在流程内部
  重新引入了同一种浪费。

## 决策

**任何挂车失败都立即中止流程。**

挂车是业务必须项：商品没挂上，视频发出去也没有价值，
因此不存在「挂车失败但仍值得继续」的情形。

三种失败形态仍然保留各自独立的错误码——它们指向不同的责任方，
上游需要据此给出不同的提示——但处置方式统一为立即中止。

相应地，流程上下文中不再需要「待决错误（pending error）」机制，
`PipelineContext` 因此保持为纯粹的只读上下文。

## 结果

### 收益

- 挂车失败时的返回耗时从「数分钟」降到「秒级」。
- 编排器少了一条隐式的状态传递路径，取消与错误处理的逻辑都更直白。
- 错误码语义更干净：14/21/23 各自表示一个确定的失败原因，
  而不是「可能会被后续结论覆盖的临时值」。

### 代价

- 放弃了「结合上传结果细化挂车失败原因」的可能性。
  实践中这种细化价值有限：三种错误码已经覆盖了上游需要区分的全部情形。

### 验证方式

集成测试中，挂车失败场景需断言 **错误码与总耗时上界**：
模拟页会在挂车环节注入失败，同时让上传保持长时间无结论；
若流程仍去等待上传，耗时断言会立刻变红。
