# ADR-0004 进度回报：多行 JSON、默认关闭、步骤级而非百分比

- **状态**：已采纳
- **日期**：2026-09-20

## 背景

发布一次视频要花一到数分钟，其中大部分时间耗在两处长等待上：
等视频上传完成（实测 60~70 秒起）、等发布结果。

在这段时间里，调度方从进程那里得不到任何信息。它只能看到进程还在跑，
无法回答两个很实际的问题：

1. 现在进行到哪一步了？
2. 它是**正在上传**，还是**已经卡死**？

第 2 个问题尤其要紧。一个卡死的任务和一个正常上传的任务，
在外部看起来完全一样，只能干等到总超时（默认 10 分钟）才能区分。

## 问题

加进度输出会动到一条既有契约：**stdout 有且仅有一行 JSON**。

上游若按「读最后一行」解析，加了进度行也不受影响；
但若按「读取整个 stdout 再 json.loads」解析，多出任何一行都会直接失败。

我们无法确定上游用的是哪一种。

## 决策

### 一、多行 JSON，用 `type` 区分，结果永远在最后一行

```
{"schema":1,"type":"progress","stage":"upload","step":1,"total":9,...}
{"schema":1,"type":"progress","stage":"await_upload","step":6,"total":9,...}
{"schema":1,"type":"result","ok":true,"code":0,...}
```

结果行追加 `"type": "result"`——只增字段，对既有解析无影响。

### 二、默认关闭

这是与 ADR-0003 中截图选项相反的取舍，因为两者的影响面不同：

| | 对输出的影响 | 默认 |
| --- | --- | --- |
| 失败截图 | 给结果 JSON **增加一个字段** | 开启 |
| 进度回报 | 让 stdout 从一行变成**多行** | **关闭** |

增字段是安全的，改变行数不是。在不能确定上游解析方式的前提下，
默认关闭是唯一不会悄悄弄坏对接的选择。

### 三、步骤级进度，不做百分比

进度报「第 N 步 / 共 M 步」，不报上传百分比。

百分比要从页面元素里抠。页面一改版，抠出来的数字就不对了——
而且它**不会报错**，只会安静地给出错误的数字。
一个会静默说谎的进度条，比没有进度条更糟：
调度方会基于它做超时判断，而它正在骗人。

步骤级进度完全来自我们自己的流程定义，不依赖页面结构，
页面怎么改都不会让它失真。

### 四、心跳：进度回报真正的价值

除了步骤切换时发一次，长等待期间还按固定间隔发心跳（默认 15 秒）。

这才是能回答「卡死还是正在跑」的那部分。只在步骤切换时报进度的话，
等上传的那 60 多秒里依然一片寂静，和卡死毫无区别。

心跳作为独立任务与主流程、哨兵并发运行，但 **不参与竞速**——
它永远不会「赢」，只会在流程结束时被取消。

## 结果

### 收益

- 调度方能实时展示进度，也能据此判断任务是否仍然存活。
- 默认关闭，既有对接零影响。
- 进度来源与页面结构解耦，改版不会让它失真。

### 代价

- stdout 从单行变多行（仅在显式开启时），文档需明确说明解析方式。
- 多一个并发任务，需要保证它在所有退出路径上都被取消，
  否则会留下悬挂任务。已有测试覆盖。

### 兼容性

默认关闭时输出与此前完全一致。开启后，
「读 stdout 最后一行」的解析方式仍然成立。
