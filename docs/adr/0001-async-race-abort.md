# ADR-0001 采用 asyncio 事件竞速中止模型

- **状态**：已采纳
- **日期**：2026-09-20

## 背景

自动化发布流程由若干步骤串联而成，其中两处存在不可预估的长等待：

1. 视频上传完成 —— 取决于文件大小与网络状况，可达数分钟。
2. 发布结果返回 —— 取决于平台审核前置校验，数秒到数十秒。

与此同时，页面会以 **轻提示（toast）** 的形式，在任意时刻异步抛出终局性的坏消息：
上传失败、服务异常、商品不支持推广。这些提示一旦出现，任务结局就已确定。

问题在于：**坏消息的到达时刻，与程序当前所处的等待点，是完全解耦的。**

## 问题

若采用「顺序执行 + 在特定点轮询消息队列」的结构，感知延迟等于
「从消息到达，到下一次轮询」的间隔——而这段间隔里往往正阻塞在某个长等待上：

```
t=0s     开始上传
t=3s     页面弹出「上传失败」         ← 结局此刻已定
t=3s     程序正阻塞在「等待挂车弹窗」的元素查找上，看不到这条消息
...
t=303s   终于走到等待上传的轮询点，此时该点自身已超时
         返回「上传超时」             ← 时间白白浪费，且错误码是错的
```

两个代价：

- **时间成本**：本可秒级失败的任务占满整个上传等待窗口，拖慢上游的任务吞吐。
- **准确性成本**：最终返回的是「超时」而不是「上传失败」，责任归属被错判，
  上游的重试决策随之出错。

## 考虑过的方案

### A. 在每个等待点插入消息检查

在所有循环里加入队列轮询。

否决理由：无法覆盖 Playwright 内部的等待（如 `wait_for` 的 30 秒阻塞）。
只要有一处遗漏就会退化回原状，且这种遗漏无法被静态检查发现，只能靠自律，不可靠。

### B. 后台线程监听 + 主线程执行

开一个线程消费消息，命中致命消息后终止主线程。

否决理由：

- Playwright 同步 API 绑定创建它的线程，跨线程操作是未定义行为。
- Python 没有安全的线程强制终止原语。`ctypes` 注入异常的做法无法在阻塞的
  系统调用中生效，恰好在长等待场景中失效——正是最需要它的地方。

### C. asyncio 任务竞速 + 协作式取消（采纳）

把主流程和哨兵各自封装为一个 `asyncio.Task`，并发运行，用
`asyncio.wait(..., return_when=FIRST_COMPLETED)` 取先出结论者。

## 决策

采用方案 C，并配套以下约束：

1. 全链路使用 `playwright.async_api`，所有页面操作都是 `await` 点。
2. **异步路径中禁止 `time.sleep` 及任何同步阻塞调用。**
   它会钉死事件循环，使哨兵失去调度机会，导致本机制完全失效。
3. 浏览器上下文的关闭置于 `finally`，确保取消路径上资源同样被释放。
4. 取消后必须 `await` 被取消的任务并吞掉 `CancelledError`，避免悬挂任务警告。

## 结果

### 收益

- 致命提示出现后，进程在一个调度周期内退出，不再空耗超时窗口。
- 错误码反映的是 **真实的首个失败原因**，而非兜底的超时码，上游重试决策随之正确。
- 新增一类致命事件只需在事件翻译表中加一行，哨兵逻辑无需改动。

### 代价

- 全链路异步带来一定的心智负担，所有 I/O 必须保持异步纯度。
- 取消语义需要专门的测试保障（含耗时上界断言），否则退化难以察觉。

### 验证方式

见 [测试策略 3.3](../testing.md)：对竞速中止的每条路径断言错误码 **与总耗时上界**。

这两条断言缺一不可，已由变异验证证实。把 `_run_sentinel` 改成「命中致命事件也
不中止」后重跑 `test_致命提示被哨兵捕获并立即中止`：

| | 单条耗时 | 返回的错误码 |
| --- | ---: | --- |
| 现状 | 0.45s | `PRODUCT_NOT_SUPPORTED(22)` — 真实原因 |
| 变异 | 37s | `UPLOAD_TIMEOUT(11)` — 兜底超时码 |

两条断言各自抓住了退化的一个侧面：错误码断言抓住了「责任归属被错判」，
耗时断言抓住了「时间被白白浪费」。

（37 秒是测试里 40 秒总预算的上限所致；生产配置下，
流程会一直空等到 300 秒的上传等待窗口用尽。）
