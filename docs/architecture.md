# 架构设计

> 本文档描述「抖音视频自动发布器」的整体架构、分层职责与关键机制。
> 阅读顺序建议：本文 → [CLI 协议](./cli-protocol.md) → [错误码契约](./error-codes.md) → [测试策略](./testing.md)。

## 1. 项目定位

本项目是一个 **一次性命令行任务进程**：由上游调度方（桌面端应用）以子进程方式拉起，
接收一份任务配置，驱动本机 Chrome 完成抖音创作者中心的「视频上传 → 信息填写 → 挂车 → 发布」全流程，
并以 **进程退出码 + 结构化 JSON 结果** 向上游回报执行结论。

三条不可动摇的设计红线：

| 红线 | 说明 |
| --- | --- |
| **单次任务、进程即边界** | 不常驻、不守护、不维护任务队列。崩溃即失败，由上游负责重试。 |
| **失败必须立刻返回** | 任何已经可判定为失败的状态，都不得继续占用剩余的等待窗口。 |
| **错误必须可分类** | 上游要能仅凭退出码判断「该不该重试」，不需要解析日志文本。 |

## 2. 核心机制：事件竞速中止（Race-to-Abort）

这是整个项目最重要的设计，也是全异步架构存在的理由。

### 2.1 要解决的问题

网页发布流程存在大量 **长等待**：视频上传需数十秒到数分钟，发布结果需数秒到数十秒。
如果按「顺序执行 + 到点轮询」的方式编写，会出现一种严重浪费：

> 页面在第 3 秒就弹出了「上传失败」的轻提示，而程序正阻塞在第 5 步的元素等待里，
> 要一直耗到 10 分钟总超时才会醒来，最终返回一个 3 秒前就已确定的结论。

对上游而言，这意味着一个 **本可秒级失败的任务，占用了十分钟的调度槽位**。

### 2.2 解决方案

把「主流程」和「哨兵」作为两个并发任务同时运行，谁先出结论谁说了算：

```
                    ┌──────────────────────────────────────────┐
                    │        asyncio 事件循环（单线程）         │
                    └──────────────────────────────────────────┘
                                      │
              ┌───────────────────────┴───────────────────────┐
              │                                               │
     ┌────────▼─────────┐                          ┌──────────▼──────────┐
     │    主流程任务     │                          │   致命事件哨兵任务   │
     │  pipeline_task   │                          │    sentinel_task    │
     ├──────────────────┤                          ├─────────────────────┤
     │ 1 上传视频        │                          │ 持续消费事件总线：   │
     │ 2 填标题标签      │                          │  · 上传失败          │
     │ 3 发布设置        │   ◀── 取消（cancel）──   │  · 服务异常          │
     │ 4 自主声明        │                          │  · 商品不支持        │
     │ 5 挂载购物车      │                          │  一旦命中 → 立即完成 │
     │ 6 等待上传完成    │                          └─────────────────────┘
     │ 7 设置封面        │                                     ▲
     │ 8 点击发布        │                                     │
     │ 9 等待发布结果    │                          ┌──────────┴──────────┐
     └────────┬─────────┘                          │       事件总线       │
              │                                    │    asyncio.Queue    │
              │  正常完成 ──▶ 取消哨兵              └──────────▲──────────┘
              │                                               │
              └──────────── asyncio.wait(FIRST_COMPLETED) ────┘
                                                              │
                                              ┌───────────────┴───────────────┐
                                              │  浏览器页面注入的 DOM 观察器   │
                                              │ MutationObserver → 回调 Python │
                                              └───────────────────────────────┘
```

执行语义：

1. 两个任务同时启动，用 `asyncio.wait(..., return_when=FIRST_COMPLETED)` 等待。
2. **哨兵先完成** → 说明页面已抛出致命提示，立即 `cancel()` 主流程，按哨兵给出的错误码退出。
   主流程无论当前卡在哪个 `await`，都会在下一个调度点收到 `CancelledError` 并退出。
3. **主流程先完成** → 取消哨兵，按主流程结论退出。
4. **总超时兜底** → 外层统一封顶，防止两者都不出结论。

### 2.3 为什么不是线程或轮询

| 方案 | 问题 |
| --- | --- |
| 同步 + 轮询队列 | 只能在显式轮询点感知事件，阻塞在元素等待时完全失聪。正是本设计要消除的缺陷。 |
| 多线程 | Playwright 同步 API 不允许跨线程共享；且 Python 没有安全的线程强制终止原语，「取消」无法可靠实现。 |
| **asyncio（采用）** | Playwright 原生提供 async API；`Task.cancel()` 是语言级的协作式取消，能在任意 `await` 点生效。 |

详见 [ADR-0001](./adr/0001-async-race-abort.md)。

## 3. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  接口层  cli/                                                │
│  参数解析 · 子命令分发 · 退出码与 JSON 结果输出               │
└───────────────────────────┬─────────────────────────────────┘
                            │ 依赖向下，绝不反向
┌───────────────────────────▼─────────────────────────────────┐
│  编排层  pipeline/                                           │
│  流程定义 · 步骤顺序 · 竞速中止 · 步骤异常到错误码的映射      │
│  ├─ runner.py    竞速编排器                                  │
│  ├─ context.py   流程上下文（配置 + 页面 + 事件总线）         │
│  └─ steps/       每个业务步骤一个模块，单一职责               │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  能力层  browser/ · system/                                  │
│  browser/  浏览器启动 · 页面动作原语 · 事件注入与采集         │
│  system/   进程清理（浏览器残留、外部剪辑软件）               │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  基础层  core/ · config/                                     │
│  core/    错误码体系 · 异常类型 · 日志 · 异步等待原语          │
│  config/  任务配置模型 · 解析与校验                           │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向向下。** 基础层不感知业务，能力层不感知流程顺序，编排层不直接操作 DOM。

### 4.1 选择器集中登记

所有 CSS / XPath 选择器统一收敛到 `browser/selectors.py`，业务步骤中不出现裸字符串。
目标页面是第三方站点、随时可能改版；集中登记后，改版应对成本从「翻遍全仓」降为「改一个文件」。

## 5. 关键模块说明

### 5.1 core/errors.py — 错误契约的唯一真相源

错误码不是散落在各处的 `sys.exit(17)` 魔法数字，而是一个带元信息的枚举：

- `code`：进程退出码
- `retryable`：上游是否应当重试
- `category`：责任归属（配置 / 环境 / 用户 / 平台 / 商品 / 程序）
- `message`：默认中文描述

业务代码抛出携带错误码的异常，由编排层统一翻译成退出码，**不允许在业务层直接调用 `sys.exit`**。
这保证了「浏览器一定会被关闭」「JSON 结果一定会被输出」。

### 5.2 core/events.py — 事件总线

浏览器端的 DOM 观察器捕获轻提示文本 → 回调进 Python → 翻译为带语义的事件类型 → 投递到 `asyncio.Queue`。

事件分两类：

- **致命事件**：哨兵一旦收到立即中止全流程（上传失败、服务异常、商品不支持）。
- **进度事件**：由主流程按需等待（上传成功、发布成功、发布失败）。

总线本身不含业务判断，语义翻译在 `browser/toast.py` 完成，便于单独测试。

### 5.3 pipeline/steps/ — 步骤即单元

每个步骤是一个 `async def run(ctx) -> None` 协程，只做一件事，失败时抛出带错误码的异常。
步骤之间不共享状态，全部经由 `PipelineContext` 传递。

这样做的收益：步骤可独立测试、可独立跳过、可调整顺序，新增步骤不触碰既有代码。

### 5.4 挂车失败的延迟判定

挂载购物车存在一类特殊情形：失败原因需要结合后续的上传结果才能最终定性
（挂车上限、商品下架属于可立即定性的不可重试错误；而一般性挂车异常允许流程继续观察）。

处理方式是在上下文中记录一个 **待决错误（pending error）**：步骤不立刻中止，
而是在后续等待点一旦有结论就优先返回该待决错误。
此行为在 `pipeline/runner.py` 中显式实现并有专项测试覆盖。

## 6. 并发与资源安全

- **单事件循环、单浏览器上下文**：不做多任务并发，避免共享 Chrome 用户数据目录导致的状态污染。
- **启动前清场**：启动浏览器前，先按用户数据目录精确清理残留进程，避免「目录被占用」导致的启动失败。
- **退出必清理**：浏览器上下文的关闭放在 `finally` 中，含超时保护，确保取消路径上也不残留进程。
- **取消安全**：所有等待原语基于 `asyncio.sleep` 与 Playwright 的 async 等待，均为可取消点。
  **禁止在异步路径中使用 `time.sleep`**，否则会把整个事件循环钉死，哨兵将失去响应能力。

## 7. 日志与可观测性

| 通道 | 内容 | 消费者 |
| --- | --- | --- |
| stderr | 带阶段标记的人类可读中文日志 | 开发者、排障 |
| stdout | 最后一行输出单行 JSON 结果 | 上游程序 |

分流的原因：上游可以直接读取 stdout 的最后一行解析结果，无需在混杂的日志里做正则匹配。

## 8. 明确不做的事

- 不做账号登录与验证码处理：依赖用户数据目录中已有的登录态，未登录直接报错返回。
- 不做视频剪辑、转码、封面生成。
- 不做任务持久化、重试、限流：这些属于上游调度职责。
- 不做跨平台适配：目标平台明确为 Windows。
